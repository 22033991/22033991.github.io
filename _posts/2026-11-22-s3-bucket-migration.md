예전에 한 고객사의 그룹웨어를 통째로 마이그레이션한 적이 있다. 서버에서 서버로 옮기는 작업이었고, 그중 첨부파일은 오히려 단순한 편이었다. 새 서버에 볼륨 경로를 만들고, 기존 서버의 첨부파일 폴더 트리를 그대로 복사해 붙여 넣었다. 파일이 많아 시간이 오래 걸렸을 뿐 따로 돈이 드는 일은 아니었고, 폴더 구조만 그대로 두면 애플리케이션도 같은 경로로 파일을 찾았다.

S3를 공부하다가, 그 첨부파일이 S3에 있었다면 어떻게 옮겼을지 궁금해졌다. 일반적인 S3 버킷에는 폴더가 없다. 콘솔에서는 폴더처럼 보이지만 실제로는 `contents/2016/03/abc.pdf` 같은 key 문자열이 객체마다 하나씩 붙어 있을 뿐이다. 그러니 폴더 트리를 통째로 옮긴다는 동작도 없고, key 하나하나를 새 버킷에 복사한 뒤 원래 객체를 따로 지워야 한다. 파일이 만 개면 복사 요청도 만 번이다.

여기서부터 서버 복사와 계산이 달라졌다. 서버끼리 옮길 때는 용량과 시간만 신경 쓰면 됐는데, S3는 요청마다 요금이 붙는다. 같은 리전 안의 버킷끼리는 전송 요금 없이 복사 요청 요금만 내지만, 리전을 넘어가면 용량만큼 전송 요금이 붙어서 이쪽이 훨씬 커진다. 원래 버킷을 지우기 전까지는 두 버킷의 저장 요금이 같이 나가고, 최소 보관 기간이 있는 클래스라면 그 기간을 채우기 전에 지운 만큼도 요금을 낸다.

객체가 수백만 개라면 S3 Batch Operations로 복사 작업을 한꺼번에 돌릴 수 있다. 처음엔 이게 제일 싼 방법인 줄 알았는데, 찾아보니 작업당 요금과 객체 수에 따른 요금이 복사 요청 요금 위에 더 붙는다. 요금만 따지면 CLI로 직접 복사하는 쪽이 싸다. 대신 완료 보고서를 켜 두면 객체마다 성공했는지 실패했는지가 남아서, 실패한 것만 골라 다시 돌릴 수 있다.

서버 마이그레이션 때는 복사가 끝나면 DB 쿼리로 건수를 맞춰 보고 문서 몇 개를 골라 직접 열어 보는 정도로 확인했다. 파일을 전부 열어 볼 수는 없으니 나머지는 믿고 넘어갈 수밖에 없었는데, 객체마다 결과가 남는다는 점이 그래서 더 와닿았다.

복사하면 무엇이 같이 따라가는지도 서버와 달랐다. CopyObject는 메타데이터와 태그는 가져가지만, 스토리지 클래스는 따로 지정하지 않으면 Standard로 들어가고 암호화는 대상 버킷의 기본 설정을 따른다. Glacier Flexible Retrieval이나 Deep Archive에 들어간 객체는 복원부터 해야 복사가 되고, Glacier Instant Retrieval은 복원 없이 바로 복사된다.

권한은 아예 다른 이야기였다. 서버에서는 파일 권한이 파일과 같이 넘어갔는데, S3에서는 파일에 권한이 붙어 있지 않고 버킷 정책과 IAM 정책이 정한다. 그래서 복사를 돌리는 쪽에 원본을 읽고 새 버킷에 쓸 권한을 따로 줘야 하고, 버킷 정책이나 수명주기 규칙도 새 버킷에 다시 걸어야 한다. 정책이 key prefix 단위로 걸리니, 서버 때 폴더 구조를 그대로 두었던 것처럼 key 규칙은 건드리지 않고 버킷만 옮길 생각이다.

10년 전 첨부파일 같은 건 S3 Glacier Instant Retrieval에 넣으면 좋겠다는 생각도 했었다. 거의 열어 보지 않지만 열 때는 바로 보여야 하는 파일에 맞춘 클래스라 저장 단가가 Standard보다 싸다. 서버 디스크에 쌓아 두는 것보다 효율적일 줄 알았는데, 꺼낼 때마다 꺼낸 용량만큼 요금이 붙고, 최소 보관 기간이 90일이라 그 전에 지우거나 옮기면 남은 기간 요금을 낸다. 128KB보다 작은 객체도 128KB로 계산되는데, 그룹웨어 첨부파일은 대부분 작은 문서라 이게 꽤 걸렸다.

그렇다고 S3로 옮길 이유가 없는 건 아니다. S3 Standard는 객체를 한 리전 안에서 최소 세 개의 가용 영역에 나눠 저장하고, 1년 기준 내구성을 99.999999999%로 설계해 뒀다. 서버에 파일을 둘 때는 디스크가 죽을 때를 대비해 RAID와 백업을 직접 챙겼는데, 그 부담이 많이 줄어든다. 다만 누가 실수로 지운 파일은 버전 관리를 켜 둬야 되살릴 수 있다.

속도 쪽에서는 CloudFront가 있다. 사용자와 가까운 엣지 로케이션에서 파일을 내려주니 해외 사용자가 서울 리전 버킷의 파일을 받을 때 훨씬 빨라진다. 처음에는 이걸 붙이면 어디서든 속도 걱정이 없을 줄 알았는데, 엣지 캐시에 없는 파일은 S3까지 가서 가져와야 해서 그만큼 느리다. 그룹웨어 첨부파일은 같은 파일을 여러 사람이 반복해서 받는 일이 드물다. 게다가 첨부파일은 권한이 있는 사람만 받아야 해서, 지금 쓰는 S3 presigned URL 대신 CloudFront 서명 URL을 발급하도록 코드를 바꿔야 한다.

내가 맡았던 사이트는 대부분 사용자가 적었고, 클라우드를 쓰더라도 S3 없이 EC2에 붙은 디스크에 첨부파일을 뒀다. 사용자도 국내에 있고 파일도 많지 않은 곳에서는, S3로 옮겨서 얻는 내구성과 속도보다 옮기고 쌓아 두고 꺼낼 때마다 붙는 요금이 더 크게 보였다.
