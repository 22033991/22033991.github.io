레거시 시스템의 결재 양식을 신규 그룹웨어로 이관하는 작업을 맡았다.

이관 대상은 크게 두 종류였다.

1. 같은 회사의 구형 솔루션에서 쓰던 Java 8 기반 양식
2. 다른 회사의 그룹웨어에서 쓰던 양식

두 시스템은 양식을 저장하고 표현하는 방식이 달랐다. 하나의 변환기로 다 처리하는 것보다 원천 시스템별로 도구를 따로 만드는 게 안전할 것 같아서, 룰 기반 변환기를 두 개 만들었다.

그러고 나서 본사에서 개발한 LLM 기반 변환기까지 배포되면서, 프로젝트 안에 같은 목적을 가진 도구가 세 개 있게 됐다.

- 본사의 LLM 기반 변환기
- export 파일을 처리하는 도구 B
- 이기종 AS-IS 시스템에서 양식을 수집하는 도구 C

셋 다 레거시 양식을 신규 그룹웨어에서 쓸 수 있는 형태로 바꾼다. 그런데 입력을 해석하고 결과를 만드는 방식은 완전히 달랐다.

## 본사 도구를 기다리지 않고 직접 만든 이유

처음에는 본사에서 개발 중인 변환기를 쓸 생각이었다. 그런데 그때는 아직 기능이 완성되지 않았고 수정과 배포를 반복하고 있었다. 일정상 안정화될 때까지 기다릴 수가 없어서 직접 만들기로 했다.

목표는 두 가지였다.

- 변환 결과를 관리자 페이지에서 업로드할 수 있는 ZIP 형태로 만든다.
- 기존 백엔드의 import 기능과 파싱 로직은 최대한 건드리지 않는다.

신규 시스템 내부를 고치는 대신, 기존 import 규격에 맞는 파일을 밖에서 만들어 넣는 방식이다. 운영 코드에 미치는 영향이 적고, 잘못돼도 변환 결과만 다시 만들면 된다는 게 좋았다.

이 과정에서 클로드를 썼다. 도구를 빨리 만들 수 있었던 게 AI가 코드를 대신 써줘서만은 아니라고 생각한다. 내가 원천 시스템과 신규 시스템의 차이를 알고 있었고, 어떤 값을 유지하고 어떤 값을 바꿔야 하는지 판단할 수 있었기 때문이다. AI가 속도를 올려주긴 했지만 변환 규칙을 정한 건 결국 도메인 지식과 갭 분석이었다.

## 도구 B — 아는 규격이라 수월했다

도구 B는 구형 본사 시스템의 export 파일을 입력으로 받는다.

이 파일은 전에도 다뤄봐서 구조와 import 규격을 비교적 잘 알고 있었다. 원천 컴포넌트와 신규 시스템 컴포넌트를 대응시키는 것도 어렵지 않았다.

문제는 필드 매핑이 아니라 기능 차이 쪽이었다.

구형 시스템에서는 쓰던 기능인데 신규 시스템에는 없는 것들이 있었고, 이름은 남아 있지만 더 이상 같은 방식으로 동작하지 않는 것도 있었다. 이런 항목은 기술적으로 변환이 되느냐보다 신규 시스템에서 뭘로 대체할지를 먼저 정해야 했다.

일부는 제거하고 일부는 신규 컴포넌트로 대체했다. 자동으로 결정할 수 없는 항목은 담당자들과 처리 기준을 협의했다. 구현보다 이 기준을 합의하는 데 시간이 더 걸렸던 것 같다.

## 도구 C — 운영 화면부터 긁어야 했다

도구 C의 원천 시스템에는 export 파일이 아예 없었다. 그래서 운영 화면을 직접 크롤링해 양식 HTML과 메타데이터를 수집해야 했다.

HTML 구조도 신규 시스템과 많이 달랐다. 특히 양식 하나를 표현하는 데 컬럼을 수십 개씩 쓰는 그리드 구조가 문제였다. 원본 구조를 그대로 옮기면 결과물은 나오지만 나중에 사람이 수정하거나 유지보수하기가 어려웠다.

그래서 화면 모양만 복제하지 않고, 불필요한 컬럼을 줄이고 `colspan`과 `rowspan`을 써서 구조를 다시 만들었다. 어디까지 단순화해야 원본 배치를 유지하면서도 편집 가능한 HTML이 되는지 보려고 프롬프트와 규칙을 몇 번씩이나 고쳤다.

컴포넌트 매핑 자체는 생각보다 수월했다. 제품마다 이름과 마크업은 달라도 결재 양식에 필요한 기능은 대체로 비슷하기 때문이다. 결재선, 작성자, 부서, 작성일, 제목처럼 업무에서 요구되는 정보는 솔루션이 달라져도 크게 달라지지 않았다.

도구 C를 만들기 전에 이미 도구 B로 양식 100종을 이관한 상태였다. 그때 정리한 구현 계획과 변환 규칙을 클로드에 주고 그걸 토대로 C의 구현 계획을 쓰게 했다. 첫 번째 도구에서 얻은 지식이 두 번째 도구의 기준이 된 셈이다.

이 도구들로 양식을 옮기는 과정에서 이슈도 꽤 다양하게 겪었는데, 그건 차차 쓰기로 한다.

## 뒤늦게 완성된 세 번째 도구

두 종류의 양식 이관을 마무리할 무렵 본사의 LLM 기반 변환기가 배포됐다.

이미 작업은 끝났지만 같은 문제를 푸는 세 도구가 어떻게 다른지 궁금했다. 코드를 놓고 비교해보니 목적지는 같은데 전략이 꽤 달랐다.

| 구분 | 본사 도구 | 도구 B | 도구 C |
|---|---|---|---|
| 원천 | export, PDF, 이미지 | export | AS-IS 운영 화면 |
| 변환 방식 | LLM이 양식을 해석하고 재작성 | jsoup 기반 DOM 변환 규칙 | cheerio 기반 템플릿 조립 |
| 실행 결과 | 실행에 따라 달라질 수 있음 | 동일 입력에 동일 결과 | 동일 입력에 동일 결과 |
| 실행 중 토큰 사용 | 있음 | 없음 | 없음 |
| 반영 방식 | Admin API 및 DB 직접 입력 | ZIP 생성 후 관리자 import | ZIP 생성 후 관리자 import |
| 자동 검증 | 별도 테스트 없음 | 47개 테스트 케이스 | 4종의 probe 진단 |

셋 다 개발할 때는 클로드를 썼다. 그런데 실제로 변환을 실행할 때 LLM을 호출하는 건 본사 도구뿐이다.

도구 B와 C는 AI의 도움으로 만들었지만 완성된 프로그램은 미리 정의한 규칙만 실행한다. 같은 입력을 주면 항상 같은 결과가 나온다.

## 세 도구는 정말 경쟁 관계였을까

비교하기 전에 먼저 확인할 게 있었다. 셋이 실제로 같은 입력을 두고 경쟁하는지다.

원천별 지원 범위는 이랬다.

```text
export
├─ 본사 도구
└─ 도구 B

PDF·이미지 등 비정형 파일
└─ 본사 도구

AS-IS 운영 화면
└─ 도구 C
```

본사 도구와 도구 B는 export 영역에서 겹친다. 그런데 PDF와 이미지 같은 비정형 입력은 본사 도구만 처리할 수 있다.

반대로 도구 C가 맡은 AS-IS 시스템에는 export 파일이라는 개념 자체가 없었다. 화면의 HTML과 매크로 문자열을 직접 긁어와야 해서 이 영역은 다른 두 도구로 대체할 수 없었다.

그러니까 셋은 일부가 겹칠 뿐 완전한 대체 관계는 아니었다.

## 토큰 비용을 추정해봤다

본사 도구는 실제 이관에 써보지 않아서 실사용 비용을 잴 수는 없었다. 대신 변환 규칙과 대상 파일 크기를 기준으로 예상 토큰 사용량을 계산해봤다.

| 항목 | 추정치 |
|---|---:|
| 매 호출마다 읽는 변환 규칙 | 약 14,000토큰 |
| 양식 HTML 1건 | 약 10,000토큰 |
| 양식 약 93건을 한 번 변환할 때 | 입력 약 1,700만 / 출력 약 120만 토큰 |
| 예상 비용 | 전체 약 40~60달러, 건당 약 0.5달러 |

모델과 과금 정책, 실제 프롬프트 구성에 따라 달라질 수 있는 추정치다. 그러니 이 숫자를 본사 도구의 확정 비용으로 볼 수는 없다.

다만 구조적인 차이는 분명하다. LLM 기반 변환기는 다시 실행할 때마다 토큰을 쓰고 실행별로 결과가 조금씩 달라질 수 있다. 도구 B와 C는 개발이 끝난 뒤에는 추가 토큰 없이 반복 실행할 수 있고 같은 입력에 같은 결과를 낸다.

반복 실행과 결과 검증이 잦은 이관 작업에서는 이 차이가 작지 않았다.

## 룰 기반의 비용은 다른 데 있었다

룰 기반이라고 해서 만드는 게 더 단순한 건 아니었다. 비용이 실행 시점이 아니라 설계 시점에 붙는다.

도구 B의 핵심 변환 클래스에는 private 메서드가 68개 있다. 그중 주요 변환 과정만 26단계고, 여러 단계가 실행 순서에 의존한다.

예를 들어 특정 셀을 헤더로 승격한 뒤에 컬럼 폭을 계산해야 하는 규칙이 있었다. 두 단계의 순서가 바뀌면 새로 승격된 셀이 첫 번째 컬럼의 폭 규칙에 걸리면서 전체 레이아웃이 달라졌다.

```java
// 헤더 셀을 먼저 확정한 뒤 컬럼 폭을 계산해야 한다.
// 순서가 바뀌면 승격된 셀에 첫 열 너비 규칙이 적용된다.
```

이런 제약은 코드 곳곳에 주석으로 남겨야 했다.

순서가 잘못돼도 프로그램이 바로 실패하지는 않는다. 변환은 끝나는데 결과가 조용히 깨지는 쪽이 더 위험했다. 실제로 한 단계의 순서가 어긋나면서 에디터 ID가 전부 `editor_1`로 뭉개진 적이 있었다. 주석과 테스트 케이스가 늘어난 게 대부분 이런 경험에서 나왔다.

LLM은 주변 문맥을 보고 예외를 처리한다. 룰 기반은 개발자가 예외를 먼저 찾아서 조건과 순서로 못박는다. 어느 쪽이 낫다기보다 복잡성이 어디에 놓이느냐가 다르다. 룰 기반은 실행 비용과 재현성을 얻는 대신 복잡성을 설계와 테스트 코드 쪽으로 옮긴다.

## 도구 B의 산출물이 도구 C의 기준이 됐다

도구 B와 C는 서로 다른 원천을 처리하고 Java와 TypeScript라는 다른 언어로 작성됐다. 겉으로 보면 별개의 프로그램이다.

그런데 도구 C의 일부 기본값을 정할 때 도구 B가 만든 실제 산출물을 썼다. 액션 기본값이나 필드 구성 같은 걸 임의로 정하지 않고, 도구 B로 변환한 양식 26건을 조사해서 반복적으로 나타나는 값을 C의 변환 규칙에 반영했다.

도구 B의 산출물이 도구 C의 스펙을 검증하는 기준이 된 것이다. 첫 번째 변환기에서 확인한 결과가 두 번째 변환기의 규칙으로 이어졌다.

## 셋 다 같은 처리를 한 항목들

구현 방법은 달랐는데 세 도구가 똑같이 처리한 항목도 있었다.

- 기존 결재 프로세스를 옮기지 않고 신규 플랫폼의 기본 프로세스로 교체
- 한글이 들어간 양식 alias를 ASCII 문자열로 변환
- 최신 버전 하나만 이관하고 버전 번호를 1로 초기화
- 필드의 테두리 색상, 배경색, 글꼴 같은 스타일을 신규 시스템 규격으로 통일

우연히 같은 판단을 한 건 아니다.

구형 시스템에서 쓰던 결재 프로세스가 신규 플랫폼에 아예 없는 것처럼, 선택지가 사실상 하나뿐인 항목이 많았다. 신규 플랫폼의 제약이 명확해서 구현 방식이 달라도 같은 결과에 도달한 것이다.

답이 이미 플랫폼 규격으로 정해져 있는 영역이라, LLM의 유연한 판단이 크게 필요하지 않았을 수도 있겠다 싶었다.

## 같은 규격이 세 곳에 중복됐다

세 도구를 비교하면서 더 크게 보인 문제는 LLM이냐 룰이냐가 아니었다.

신규 양식이 따라야 하는 구조와 스타일 규격이 세 가지 형태로 따로 있었다.

- 본사 도구의 마크다운 문서: 1,235줄
- 도구 B의 Java 코드: 2,127줄
- 도구 C의 TypeScript 코드: 2,174줄

같은 도메인 지식이 문서 하나와 프로그램 둘에 각각 들어가 있는 상태다. 신규 플랫폼 규격이 바뀌면 세 곳에서 영향받는 부분을 찾아 같이 고쳐야 한다.

구현체가 세 개인 것보다 규격의 원천이 하나가 아니라는 게 더 큰 유지보수 위험이라고 생각한다. 공통 규격을 구조화된 데이터로 빼고 각 변환기가 그걸 참조하게 만드는 게 낫지 않을까 싶다. 변환 규칙 전부를 공통화할 수는 없어도 색상이나 기본값, alias 규칙, 지원 컴포넌트처럼 공유 가능한 부분은 하나로 관리할 수 있을 것 같다.

## 언제 LLM을 쓰고, 언제 룰을 쓸 것인가

본사 도구를 만든 개발자와 이야기하면서 접근이 달랐던 배경도 알게 됐다.

본사 도구에는 사용자가 변환 규칙을 직접 판단하거나 결과를 많이 손대지 않아도 되게 하라는 요구가 있었다고 한다. 도메인 지식이 없는 사용자도 PDF나 이미지 같은 걸 넣어서 양식을 만들 수 있어야 했다. 토큰 비용이 들더라도 LLM이 입력을 해석하고 판단하는 방식을 택한 이유다.

그 목표라면 LLM 쪽이 자연스럽다. 입력이 비정형이고 어떤 형태가 들어올지 개발자가 다 예상하기 어렵기 때문이다. 다양한 문서를 규칙만으로 해석하려면 예외 처리가 금방 불어난다.

도구 B와 C가 다루는 원천은 구조가 정해져 있었다. 변환 규칙을 만드는 초기 비용은 들지만 이후에는 같은 결과를 반복해서 만들 수 있다. 대량 이관처럼 재실행과 검증이 반복되는 작업에서는 결정성과 실행 비용이 더 중요했다.

솔직히 그때는 개발하면서 쓰는 토큰도 부담스러웠다. 그래서 LLM이 꼭 판단해야 하는 영역과 코드로 고정할 수 있는 영역을 계속 구분했다. 사람이 도메인 지식으로 규칙을 확정할 수 있다면 실행할 때마다 LLM에 같은 판단을 맡길 필요는 없다고 봤다.

도구를 고를 때 실제로 따져본 건 이런 것들이었다.

- 입력 형식을 예측할 수 있는가
- 변환 기준을 규칙으로 표현할 수 있는가
- 같은 입력에 같은 결과가 필요한가
- 얼마나 자주 다시 실행해야 하는가
- 사용자가 도메인 지식을 갖고 있는가
- 예외를 코드로 관리하는 비용이 LLM 실행 비용보다 큰가

이번 작업에서 AI는 두 역할을 맡았다. 본사 도구에서는 실행 시점에 양식을 해석하는 변환 엔진이었고, 내가 만든 두 도구에서는 개발을 돕는 도구였다. 같은 프로젝트 안에서 두 방식을 다 겪어보니, AI를 썼는지 안 썼는지보다 어디까지를 AI에 맡기고 어디부터 코드로 고정할지를 정하는 쪽이 더 중요했던 것 같다.
