근태 모듈을 만들다가 "컬럼 하나만 추가하면 되겠지" 했던 요구가 모델을 둘로 가르는 결정이 된 이야기를 적어 둔다. 그때 내린 판단을 지금 아는 도메인 용어로 다시 읽어 보려고 쓴다.

요구는 단순했다. 회사마다 근태코드를 자기 방식대로 정의하게 해 달라는 것이었다. 당시 근태코드는 제품 전체가 공유하는 공통 코드표에 들어 있었다. 전사 공통이라는 건 A사가 코드를 추가하거나 미사용 처리하거나 정렬을 바꾸면 그게 모든 계열사 화면에 그대로 반영된다는 뜻이다. 요구를 들어주려면 이 구조를 깨야 했다. 처음 떠올린 해법은 가장 쉬운 것이었다. 공통 코드표에 회사 컬럼을 하나 넣으면 끝날 것이라고 생각했다.

그런데 이 표를 쓰는 게 근태만이 아니었다. 표 위에는 회사 구분이 없는 코드 캐시와 AOP가 얹혀 있었고, 게시판이나 결재, 기록물처럼 근태와 전혀 상관없는 기능도 같은 표를 읽고 있었다. 다국어 이름을 담는 테이블은 이 표의 키에 직접 걸려 있어서 회사를 끼워 넣을 자리가 없었다. 회사 컬럼을 넣는 순간 근태와 무관한 기능까지 같이 흔들린다. 처음엔 컬럼 하나 넣는 데 왜 이렇게 걸리는 게 많은지 의아했는데, 들여다볼수록 컬럼의 문제가 아니라는 생각이 들었다. "근태코드"라는 같은 말이 서로 다른 두 개념을 가리키고 있었다. 공통 기반 쪽에서 보면 전사가 같이 쓰는 코드 한 행이고, 근태 쪽에서 보면 회사가 스스로 정하는 정책이다. 이름은 같은데 바뀌는 이유도, 바꾸기로 결정하는 주체도 달랐다. 이걸 한 모델에 억지로 담으려던 게 문제였다.

그래서 근태 전용으로 회사별 테이블을 따로 세웠다. 근태코드, 근태유형, 근태설정이 각자 테이블을 갖고, 다국어 이름도 같은 이유로 별도 테이블로 뺐다.
설계에서 가장 신경 쓴 건 키였다.

```java
@Entity
@Table(name = "...")           // 회사별 근태코드 테이블
@IdClass(CefAttCode.ID.class)
public class CefAttCode extends BaseEntity {
    public static class ID implements Serializable {
        private String companyId;
        private String cd;
    }
    @Id private String companyId;
    @Id private String cd;
    ...
}
```

`(회사, 코드)` 복합키다. 회사를 식별자 안에 넣은 것이다. 이제 신규 회사는 행을 넣는 것만으로 자기 코드체계를 갖고, 다른 회사나 다른 기능은 영향을 받지 않는다.

겉으로는 테이블을 하나 더 만든 것처럼 보이지만, 실제로 시간이 든 건 경계를 어디에 그을지 정하는 쪽이었다.

## 옛 모델은 지우지 않았다

새 테이블을 만들었다고 기존 것을 걷어내지는 않았다. 기존 근태 경로는 코드를 상수로 하드코딩해 두고 공통 코드표를 읽는다. 여기를 건드리면 이미 돌고 있는 기능이 깨진다. 그래서 옛 행은 그대로 두고 새 테이블이 새 화면의 기준이 되도록 일부러 두 체계를 공존시켰다. 출퇴근 실적처럼 양쪽이 함께 쓰는 데이터는 공유하고, 정책에 해당하는 마스터만 갈랐다.

공존에는 비용이 따랐다. 코드 값이 두 곳에 존재하게 됐고, 근태유형 값은 협의가 끝나야 새 체계로 재매핑할 수 있어서 한동안 옛 값을 그대로 옮겨 놓은 상태로 남았다. 기존 모델을 깨지 않고 옆에 새 모델을 세우는 방식은 이행하는 동안엔 안전하지만, 이행이 끝날 때까지 이중 구조라는 빚을 진다. 그 빚을 주석으로 분명히 적어 두는 게 당시 할 수 있는 최선이었다.

## 연차 계산기는 한 벌만 뒀다

회사별로 가른 것과 반대 방향의 결정도 있었다. 연차 계산이다.

연차 일수를 구하는 산식은 두 군데에서 필요했다. 관리자가 연차를 생성할 때, 그리고 배치가 매달 월차를 적립할 때다. 구조상 배치 모듈은 근태 전용 패키지를 의존할 수 없었다. 가장 쉬운 길은 배치 쪽에 산식을 복사해 두는 것이었다.

그러나 복사하지 않았다. 연차는 결국 연차수당, 그러니까 돈으로 환산되기 때문이다. 산식이 두 벌이면 같은 사람의 연차가 화면과 배치에서 다르게 나올 수 있고, 그러면 수당을 계산하는 근거가 두 개가 된다.

그래서 계산기를 의존성 없는 순수한 클래스로 만들고 두 모듈이 같은 코드를 호출하게 했다. 스프링 빈으로는 만들지 않았다. 빈으로 두면 배치의 컴포넌트 스캔에 걸려 기동이 깨졌기 때문이다. 입력도 원시값만 받아서 계산기가 어떤 엔티티도 모르게 했다.

연산은 전부 `BigDecimal`로 했다. 실제로 `double`로 `18 × 0.6`을 계산하면 `10.799999999999999`가 나오고, 경계값에서 연차 사용촉진 대상 개수가 달라진다. 결과 일수는 0.125일 단위까지 다룰 수 있게 소수 셋째 자리로 정규화했고, 비례연차의 분모는 윤년이어도 365로 고정했다. 366으로 바꾸면 실데이터와 어긋났다.

만근은 달력 기준으로 한 달을 채웠는지로 보고 결근은 보지 않는다는 규칙도 이 계산기 안에 있다. 정책이 바뀌면 이 한 곳만 고치면 되고, 생성과 배치가 같은 계산법을 쓴다.

## 경계는 패키지 구조에도 번졌다

모델 경계는 결국 패키지와 모듈 구조로 이어졌다. 고객사 커스터마이징을 기본 코드 수정 없이 얹는 별도 레이어로 근태를 옮기면서, 여러 모듈이 같이 쓰는 근태 코드는 어디에 두고 모듈마다 다른 부분은 어디에 둘지가 계속 문제가 됐다.

원칙은 복제하지 않는 것이었다. 공통으로 쓰는 건 한 벌만 두고 모듈마다 달라지는 부분만 각 모듈에 뒀다. 나누는 기준은 그 코드를 쓰는 모듈의 집합으로 잡았다. 배치에 근태 마스터 빈이 생기지 않도록, 쓰는 모듈 집합에 따라 공용 위치를 둘로 나눴다. 앞의 연차 계산기도 나중에 이 레이어로 옮겼는데, 생성과 배치가 함께 쓰는 코드라 여기서도 한 벌만 뒀다.

솔직히 한 번에 맞히지는 못했다. 처음 쌓은 구조는 경계가 어긋나 있었고, 결국 작업물을 전부 버린 뒤 범위와 이름부터 다시 정해 처음부터 다시 했다. 어디까지가 이 도메인의 몫인지 코드를 쓰기 전에 합의하지 않으면 나중에 통째로 되돌리게 된다는 걸 그때 몸으로 겪었다.

## DDD라고 부를 수 있는 것과 없는 것

돌아보니 이 결정들은 도메인 주도 설계(DDD)의 용어로 꽤 잘 설명된다. DDD에는 Bounded Context라는 개념이 있다. 같은 단어도 쓰이는 영역에 따라 뜻이 달라질 수 있으니, 뜻이 갈리는 지점에 선을 긋고 모델을 따로 두라는 것이다. 이번 일이 딱 그랬다. 공통 기반에서 "근태코드"는 전사가 같이 쓰는 코드 한 줄이었고, 근태에서는 회사가 정하는 정책이었다. 공통 코드표에서 근태코드를 떼어 낸 건 결국 그 선을 그은 것이었다. 회사 컬럼을 넣지 않은 것도 같은 이유다. 근태 사정 하나 때문에 게시판이나 결재까지 같이 쓰는 표를 바꾸고 싶지 않았다.

옛 경로를 그대로 두고 새 테이블을 옆에 만든 건 처음에 Anti-Corruption Layer(ACL)라고 부르려 했다. 그런데 다시 보니 ACL은 옛 시스템과 새 시스템 사이에 통역 역할을 하는 계층을 두는 것이었다. 옛 코드 값을 받아서 새 모델이 알아듣는 값으로 바꿔 넘겨주는 식이다. 나는 그런 변환 계층을 만들지 않았고 두 체계를 나란히 세워 두기만 했다. 이건 Strangler Fig 패턴에 더 가깝다. 무화과 덩굴이 오래된 나무를 감고 자라다 결국 그 나무를 대신하듯, 옛 시스템은 그대로 둔 채 새 기능부터 새 구조로 만들고 조금씩 옮겨 가는 방식이다.

경계는 DDD식으로 잘 그었지만 그 안의 코드는 일반적인 서비스 중심 구조라서 "DDD를 적용했다"고는 말하지 못한다.

처음부터 DDD를 의식하고 만든 건 아니었는데, 바뀌는 이유가 다른 것끼리는 한 모델에 두지 않으려고 하나씩 판단하다 보니, 결과적으로 도메인 경계와 거의 같은 선이 그어져 있었다. 애초에 왜 그렇게 접근하지 못했을까 생각해 보면, 요구를 컬럼 하나의 문제로만 읽었기 때문이다.
