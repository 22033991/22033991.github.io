2024년 초, 외부 프로젝트를 쉬는 동안 타 팀에서 쓰는 사내 요청 관리 시스템을 업그레이드하는 단기 프로젝트를 맡게 됐다. 부서 담당자가 요청 건을 올리면 처리 담당자가 받아서 진행하는, 흔한 내부 사이트다. 본격적인 프로젝트 대기 중에 투입된 거라 전면적인 고도화는 아니었고, 주로 사용하는 기능들과 프론트엔드 코드 위주로 수정하고 있었다.

그러다 유지보수팀에서 일하는 동기에게 URL 관련 이슈를 전해 들었다. 담당 중인 노후화된 사이트에서 누군가 URL 파라미터를 임의로 변조해 권한이 없는 문서를 조회하는 바람에 큰 문제가 생겼다는 것이다. 이런 얘기를 들으면 '내가 짜는 코드에도 비슷한 구멍이 있지 않을까?' 하고 먼저 확인하는 게 습관이라, 진행 중이던 사이트를 바로 뒤져봤다.

아니나 다를까, 내가 담당한 사이트도 상세 화면 URL에 요청 번호가 평문으로 훤히 노출되는 구조였다.

```
/req/view.jsp?reqId=189023789
```

서버 쪽 `getReqDetail()` 코드를 열어보니 더 심각했다. 시스템에 로그인(인증)이 되어 있는지만 확인할 뿐, 정작 이 `reqId`를 조회할 권한(인가)이 있는지는 전혀 검증하지 않고 있었다. `reqId`를 받자마자 아무 의심 없이 바로 DB 조회를 때리고 있었다.

즉 사내 시스템에 로그인만 되어 있으면 URL의 숫자만 살짝 바꿔서 다른 부서 담당자가 올린 민감한 문서도 맘대로 볼 수 있는 상태였다. 나중에 찾아보니 IDOR(Insecure Direct Object Reference)이라고 이름까지 붙어 있는 취약점이었다. OWASP Top 10에서는 Broken Access Control로 분류된다.

## 처음엔 URL부터 암호화했다

일단 상세 화면을 요청하는 URL을 사내 프레임워크에서 사용하는 방식으로 암호화했다. 숫자가 그대로 보이지 않으니 당장은 해결된 것 같았다.

그런데 여기서 멈췄으면 아무것도 고친 게 아니었다. 사내 공통 암호화는 키가 고정이라 한 번 얻은 암호문이 계속 유효하다. 결국 암호문이 새로운 평문 노릇을 하는 셈이다. 자기 문서의 암호화된 URL을 복사해서 넘겨주면 받은 사람도 그대로 조회할 수 있다. 무엇보다 서버는 여전히 이 사람이 이 문서를 봐도 되는지 묻지 않는다.

URL 암호화는 식별자를 눈에 안 띄게 만드는 작업이지 접근을 막는 작업이 아니었다. 진짜 막아야 할 곳은 조회 쿼리 앞단이었다.

## 조회하기 전에 권한부터 확인

그래서 내부 사용자 분기에도 쿼리를 실행하기 전에 권한을 확인하는 코드를 끼워 넣었다.

```java
// 사용자 유형을 먼저 구분
String userKind = dataset.getUserInfo().getUserKind();

if (!ReqConstants.ACL_USER_KIND_IN.equals(userKind)) {

    String deptId = dataset.getUserInfo().getDeptId();

    if (!ReqAuthService.authChk(deptId, reqId)) {

        // 감사 기록은 로거로, 사용자에게는 일반화된 메시지만
        logger.warn("[REQ-ACL] 권한 없는 문서 접근 시도. dept={}, user={}, reqId={}",
                deptId, dataset.getUserInfo().getName(), reqId);

        throw new BusinessException("접근할 수 없는 문서입니다.");
    }
}

// 인가를 통과한 뒤에야 조회
ReqDetail detail = reqDao.getReqDetail(reqId);
```

짜면서 신경 쓴 부분은 세 가지다.

먼저 조회 전에 차단하는 것. 데이터를 DB에서 다 긁어온 다음에 "아, 이 사람은 보면 안 되네" 하고 튕겨내면 너무 늦다고 생각했다. 이미 읽어온 데이터는 로그나 에러 응답에 묻어나갈 수 있다. 인가 체크는 무조건 조회 쿼리 앞단에서 끝나야 한다.

두 번째는 불필요한 조회를 줄이는 것. `authChk()`는 DB를 한 번 더 다녀오는 함수라 모든 요청에 매번 태우는 건 낭비라고 판단했다. 그래서 사용자를 고객과 직원 타입으로 먼저 구분하고, 그 이후에 필요한 인가 처리를 진행하도록 흐름을 잡았다.

사실 여기서 `ACL_USER_KIND_IN`, 그러니까 내부 직원을 체크에서 빼는 게 처음엔 좀 걸렸다. 구멍을 하나 남겨두는 것처럼 보였기 때문이다. 확인해보니 내부 직원은 요청 처리 담당자라 부서와 무관하게 전 문서를 열람하는 것이 원래 업무 요건이었다. 이들에겐 부서 기준 인가가 애초에 성립하지 않으니 빼는 게 맞았다. 반대로 고객 사용자는 자기 부서 문서만 봐야 하니 반드시 검증을 거친다. 내부 직원이니까 믿고 통과시키는 게 아니라 실제로 권한이 부여되어 있어서 통과시키는 것이고, 그 전제가 바뀌면 이 분기도 같이 바뀌어야 한다.

세 번째는 로그다. 처음엔 예외 메시지 안에 타임스탬프랑 부서, 이름, 요청 ID를 전부 담았다. 단순히 차단 사실만 남기는 것보다 낫다고 생각했는데, 다시 보니 그건 로깅이 아니었다. 예외 메시지는 화면에 그대로 노출될 수 있어서 그 자체가 정보를 흘리는 통로가 되고, 타임스탬프는 로거가 이미 찍어주니 중복이다. 무엇보다 나중에 집계를 하려면 기록이 문자열 안에 묻혀 있으면 안 된다. 그래서 감사 기록은 `logger.warn()`으로 따로 남기고, 사용자에게는 "접근할 수 없는 문서입니다"만 보여주도록 나눴다. 나중에 유지보수하는 사람이 `[REQ-ACL]` 태그로 로그를 걸어두고 특정 사용자의 시도가 비정상적으로 많다는 걸 알게 되면, 그에 대한 대처도 훨씬 적극적으로 달라질 것이라 생각했다.

## 남은 것들

소규모 사이트이고 관계자들만 사용하는 곳이다 보니, 초창기엔 "로그인한 사람 = 신뢰할 수 있는 내부 사용자"라는 전제로 설계된 것 같았다. 실제로 그 전제가 대체로 맞았으니 지금까지 별 탈 없이 굴러왔을 것이다. 그래도 권한 체크를 한 번 더 해서 나쁠 것은 없다고 생각했다.

솔직히 이번에 막은 건 화면 하나다. 소규모 사이트이기 때문에, 내가 평소에 하는 프로젝트와 같은 규모의 것이 아니었다. 외부 프로젝트에서는 식별자로 리소스를 찾는 화면이 하나만 있을 리 없다. 화면마다 `if` 문을 손으로 끼워 넣는 건 생각보다 귀찮고, 불필요한 공수가 드는 일이다.

조회 메서드에서 `reqId` 하나만 받는 시그니처를 아예 없애고 싶기도 했다. `getReqDetail(reqId, deptId)`처럼 사용자 컨텍스트를 반드시 같이 받게 하고 쿼리 `WHERE` 절에 부서 조건을 넣으면, 권한 없는 문서는 애초에 결과에 나오지 않는다. 체크를 깜빡할 방법 자체가 사라지는 셈이다. 이전의 나는 주로 이런 방식으로 개발을 진행해왔다. 다만 이 사이트는 어디에서 저 URL과 메서드를 쓰고 있을지 모르는 일이라, 미처 변경되지 않은 호출이 남을 수 있다는 점이 부담스러웠다.

스프링을 쓰는 프로젝트였다면 인터셉터나 AOP로 공통 처리했을 텐데, 이건 자체 프레임워크에 JSP라 그런 선택지가 없었다. 지금 하고 있는 프로젝트에서는 AOP로 공통 처리하고 있다.

이번 일을 통해 리소스에 식별자로 접근하는 화면은, 그 식별자가 노출되는 순간부터 "권한이 없는 사람이 그 번호를 넣어보면 어떻게 되는가"를 항상 의심해야 한다는 기본기를 다시금 새겼다.
