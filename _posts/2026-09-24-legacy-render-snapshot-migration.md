구 그룹웨어의 결재 문서를 새 시스템으로 옮기는 작업에 참여했다. 다른 고객사에서 쓰던 이관 도구가 있었고, 내가 맡은 일은 그 도구를 새 고객사 환경에 맞추는 것이었다. 나는 주로 이미지 경로 쪽을 고쳤고, 변환에 실패한 문서를 다시 돌릴 재변환 테이블을 새로 만들었다.

그런데 도구를 고치려면 이 도구가 문서를 어떻게 옮기는지부터 알아야 했다. 코드를 읽다가 예상과 다른 구조를 발견했다. 사용자가 보던 결재 본문의 완성본이 DB 어디에도 없었다.

양식 정의는 한곳에, 사용자가 입력한 값은 다른 곳에 저장돼 있었다. 구 시스템은 문서를 열 때마다 두 데이터를 조합해 HTML 화면을 만들었다. 사용자들이 수년 동안 봐 온 문서가 사실은 열 때마다 새로 그려지고 있던 셈이다.

## 데이터를 옮길지 화면을 옮길지

방법은 두 가지였다. 양식과 입력값을 각각 추출해서 이관 도구 안에 레거시 렌더링 규칙을 다시 구현하거나, 구 시스템의 문서 화면을 직접 호출해서 이미 렌더링된 HTML을 스냅샷으로 저장하는 것이다.

첫 번째는 DB 데이터만으로 이관할 수 있다는 게 장점이다. 대신 양식 버전, 누름틀, 결재선, 외부 연계 영역까지 구 시스템의 렌더링 규칙을 이관 도구에 다시 구현해야 한다. 사실상 기존 화면 엔진의 일부를 하나 더 만드는 작업이었다. 게다가 지금은 쓰지 않아 삭제된 기능이 있다면, 그 기능도 조회만을 위해 되살려야 했다.

기존 도구는 두 번째를 골랐다. 문서 조회 화면을 실제로 호출하고, 구 시스템이 만들어 준 HTML을 받아 정적 본문으로 저장했다.

이 방식으로 작성 당시 화면을 그대로 되살렸다고 하기는 어렵다. 지금 남아 있는 렌더링 코드와 양식·리소스를 쓰기 때문이다. 그래도 렌더러를 새로 만들어 결과를 추정하는 것보다는, 그동안 사용자가 보던 조회 경로를 그대로 쓰는 쪽이 원본에 가깝다고 봤다.

## 배치는 로그인을 할 수 없었다

이관 도구는 문서를 하나씩 순회하며 구 시스템의 조회 URL을 호출했다. 문제는 인증이었다. 브라우저 로그인 세션을 가진 사용자가 없는 배치 프로그램이 문서를 열어야 했다.

그래서 마이그레이션 전용 인증 경로를 하나 뒀다. 배치가 이관용 계정 정보와 문서 식별자로 인증 파라미터를 만들어 조회 URL에 붙이면, 구 시스템이 그 파라미터로 로그인 처리를 한 뒤 그 문서의 조회 화면으로 연결했다.

```java
String documentParams = buildDocumentParams(documentKey, taskKey);

String loginParameter = migrationAuthService.createLoginParameter(
    migrationAccount,
    domain,
    documentParams
);

String html = requestHtml(viewUrl, loginParameter);
```

코드는 인증 흐름의 세부 구현이 드러나지 않도록 단순화했다.

이관용 계정은 일반 사용자가 열 수 없는 문서까지 조회해야 했다. 그만큼 권한이 큰 계정이었다. 그래서 이 진입 경로와 실행 환경을 마이그레이션 범위로 묶어두고, 작업이 끝나면 계정 권한과 전용 인증 경로를 회수하기로 했다.

작업은 전부 고객사 VPN 안에서 돌아갔다. 구 시스템도 이관 도구도 외부에서는 닿을 수 없는 망에 있었고, 배치도 그 안에서 실행했다. 인증 정보를 파라미터에 실어 보내는 방식을 쓸 수 있었던 것도 그래서였다. 외부에서 닿는 환경이었다면 이렇게는 못 했을 것 같다.

## HTTP 200인데 오류 페이지가 왔다

문서 조회에 실패해도 구 시스템은 오류 상태 코드를 주지 않았다. 사람이 볼 수 있는 오류 페이지를 HTML로 렌더링한 뒤 정상 응답으로 돌려줬다.

브라우저에서 쓰는 화면이라면 자연스러운 동작이지만, 이관 도구에는 문제가 됐다. HTTP 상태만 보면 오류 페이지를 정상 결재 본문으로 저장하게 된다.

그래서 응답 HTML 안에서 구 시스템 오류 페이지의 표식을 찾아 실패로 처리했다.

```java
String content = migrationManager.makeContentHtml(
    documentKey,
    taskKey,
    documentId,
    formAlias
);

if (content.contains(LEGACY_ERROR_PAGE_PATH)) {
    throw new MigrationException("Legacy document rendering failed");
}
```

깔끔한 방법은 아니다. 그래도 화면을 데이터 소스로 쓰기로 한 이상 어차피 해야 할 보정이었다. 다만 특정 문자열 하나에만 기대면 오류 페이지 경로가 바뀌었을 때 다시 정상으로 오인한다.

이관이 끝난 뒤에는 성공 건수만 세지 않고, 저장된 결과 중에 오류 화면이나 로그인 화면이 섞이지 않았는지 따로 훑었다.

## 화면이 두 개인 문서

일부 외부 연계 양식에는 기본 결재 본문 말고 별도의 업무 영역이 붙어 있었다. 이런 문서는 화면을 한 번 더 호출해서 두 결과를 하나의 정적 본문으로 합쳤다.

어떤 양식에 추가 호출이 필요한지는 설정으로 분리했다. 양식 별칭을 자바 조건문에 직접 넣으면 고객사나 양식이 바뀔 때마다 코드를 고쳐야 하기 때문이다.

두 HTML 문자열을 그냥 이어 붙이면 문서 구조가 깨진다. 그래서 최종 문서의 어느 영역에 추가 결과를 넣을지 위치를 정해두고 삽입했다.

## 스크립트는 걷어내고 스타일은 붙였다

받아온 HTML을 그대로 저장하지는 않았다. 브라우저에서 동작하던 화면을 장기 보관용 정적 본문으로 바꿔야 했다.

```java
content = addArchiveStyle(content);

content = removeTag(content, SCRIPT);
content = removeTag(content, IFRAME);
content = removeAttribute(content, ONLOAD);
content = removeAttribute(content, ONUNLOAD);
```

스크립트와 iframe이 남아 있으면 새 시스템에서 문서를 열 때 사라진 구 시스템을 호출하거나 예상 못 한 동작을 실행할 수 있다. 대신 본문에는 클래스 이름만 있고 스타일 정의는 구 시스템 화면에 있는 경우가 있어서, 표와 문서 배치를 유지할 CSS는 따로 넣어줬다.

다만 태그 몇 개 지웠다고 HTML이 안전해지는 건 아니다. `onclick`, `onerror`, `javascript:` URL처럼 실행 가능한 요소는 다른 형태로도 남는다. 사용자 입력이 섞인 HTML을 새 시스템에서 그대로 렌더링한다면 문자열 삭제만으로는 부족하다.

당시 처리는 레거시 화면의 동작 요소를 걷어내 정적 문서로 만드는 변환 규칙이었지, 보안 sanitizer는 아니었다. 다시 한다면 HTML 파서와 허용 목록 기반 sanitizer로 보존할 태그·속성·URL 스킴을 명시했을 것 같다.

## 이미지 경로는 한 가지 형태가 아니었다

여기부터가 내가 직접 손댄 부분이다. 도구를 현재 고객사에 맞추면서 이미지와 스타일 리소스 경로를 바꿨다. 기존 고객사에만 있던 서명·직인 절대경로를 걷어내고, 본문에 적용할 스타일도 현재 양식에 맞게 손봤다.

이미지 경로 변환에서 예상 못 한 차이가 나왔다. 같은 리소스를 가리키는 경로가 문서에 따라 절대경로이기도 하고 상대경로이기도 했다.

기존 코드는 경로가 특정 문자열로 시작하는지만 봤다.

```java
if (imageSource.startsWith(legacyThemePath)) {
    // 새 경로로 치환
}
```

현재 데이터에는 기준 문자열이 경로 중간에 나오는 문서도 있어서, 허용한 레거시 경로 목록 중 하나가 포함되는지를 보도록 바꿨다.

```java
for (String legacyPath : legacyThemePaths) {
    if (imageSource.contains(legacyPath)) {
        imageSource = StringUtils.replace(
            imageSource,
            legacyPath,
            archiveThemePath
        );
        break;
    }
}
```

이 변경으로 처리되는 문서는 늘었지만, `contains()`는 경로 일부가 우연히 맞아도 치환한다. 적용 대상을 고정된 허용 목록으로 제한하고 샘플을 검증했기 때문에 쓸 수 있었던 방식이다. 다시 구현한다면 URL을 파싱하고 경로를 정규화한 뒤 허용한 디렉터리와 맞는지 봤을 것 같다. 그러면 절대경로든 상대경로든 파서가 알아서 걸러준다.

## 중간에 실패해도 다시 돌릴 수 있게 나눴다

몇 년치 문서를 한 작업으로 돌리면 중간에 실패했을 때 어디서부터 다시 시작할지 판단하기 어렵다. 도구는 실행 기간을 설정으로 받고, 연도 단위 요청은 월별 구간으로 나눠 처리했다. 시작일과 종료일을 직접 지정해서 일부 기간만 다시 돌릴 수도 있었다.

결과 파일도 상신일자 기준으로 디렉터리를 나눠 문서 ID를 파일명으로 저장해서, 문제가 생긴 기간을 바로 찾을 수 있게 했다. 응답은 구 시스템의 인코딩으로 읽어 UTF-8로 통일했고, 문서 ID는 형식을 먼저 검증해 경로 구분자가 섞여 엉뚱한 위치에 파일이 생기는 일이 없게 했다.

문서 한 건의 실패가 이후 문서까지 멈추지 않도록 처리 단위도 나눴다. 실패한 문서 ID는 작업 마지막에 출력했지만, 로그만 남기면 배치가 끝난 뒤에 누가 그 목록을 챙겨야 한다. 그래서 변환에 실패한 문서를 따로 쌓아두는 테이블을 만들었다. 실패한 문서 ID와 실패 사유를 여기에 기록해두고, 재변환 배치가 이 테이블을 읽어 해당 문서만 다시 처리하게 했다.

덕분에 실패 건을 사람이 따로 추려낼 필요가 없어졌다. 오류 페이지를 받아서 실패한 문서든 인증이 끊겨 실패한 문서든, 원인을 고친 뒤 재변환만 돌리면 됐다.

다시 돌릴 수 있으려면 같은 문서를 두 번 처리해도 결과가 어긋나지 않아야 했다. 같은 문서 ID를 다시 처리하면 기존 파일을 덮어쓰게 했고, DB 상태와 파일 저장 중 한쪽만 성공했을 때 어떻게 되는지도 확인했다. 문서마다 트랜잭션을 나눠도 파일 시스템 작업까지 같이 묶이지는 않아서였다.

## 모든 세대의 문서를 같은 방식으로 옮기지는 않았다

고객사는 구 시스템의 서버를 유지하기로 했다. 그래서 조회 빈도가 낮을 것으로 본 과거 문서는 정적 HTML로 이관하지 않았다.

새 시스템에서 그 문서를 선택하면 같은 인증 경로를 거쳐 구 시스템의 기존 조회 화면으로 넘어가게 했다. 정적 본문 없이 구 시스템으로 넘겨주는 연결만 있는 문서다. 만드는 품은 줄었지만, 과거 문서를 보려면 구 시스템과 인증 경로를 계속 살려둬야 한다.

어느 시기 문서를 스냅샷으로 옮기고 어느 시기를 연결로 남길지는, 문서가 얼마나 자주 열리는지와 구 시스템을 언제까지 둘지를 보고 정했다.
