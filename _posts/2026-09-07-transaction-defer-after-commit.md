시스템에서 전표문서 결재를 완료하면 그 결과를 외부 회계 시스템에 전달해야 했다. 문제는 연계 시스템의 응답이 느려질 때마다 우리 쪽 DB 트랜잭션도 함께 길어졌다는 것이다.

평소에는 드러나지 않았다. 외부 API가 몇 초 안에 응답할 때는 결재 처리도 정상적으로 끝났다. 하지만 구형 연계 시스템의 응답이 지연되면 결재 데이터의 락이 그 시간만큼 유지됐고, 같은 데이터를 처리하려는 다른 요청까지 차례로 대기했다.

외부 시스템의 지연이 우리 시스템의 트랜잭션 문제로 전파되고 있었다.

## 외부 호출이 로컬 트랜잭션 안에 있었다

당시 결재 완료 처리는 하나의 트랜잭션 안에서 실행됐다. 결재 상태를 바꾸고, 문서번호를 채번하고, 외부 회계 시스템을 호출하고, 그 호출 이력을 저장한 뒤에야 트랜잭션을 커밋하는 순서였다.

외부 API가 정상적으로 응답하면 문제가 없어 보인다. 그러나 호출이 3초 걸리면 로컬 트랜잭션도 최소 3초 더 열려 있고, 10초 걸리면 그만큼 락 유지 시간도 늘어난다.

DB 트랜잭션의 수명주기가 우리가 통제할 수 없는 외부 시스템의 응답 시간에 묶여 있는 구조였다.

## 먼저 발견한 문제 — 공유 세션의 만료

연계 API는 로그인으로 발급받은 세션을 사용했다. 초기 구현은 연계사 요청에 따라 발급된 세션을 만료 시점까지 공유하는 방식이었다.

그런데 결재 처리 도중 세션이 만료되는 경우가 있었다. 외부 호출이 실패하면 예외 처리와 재시도가 이어졌고, 이미 길어진 트랜잭션이 더 오래 유지됐다.

우선 세션의 생명주기를 호출 단위로 줄였다. 호출할 때마다 세션을 새로 만들고, 호출이 끝나면 바로 삭제하는 방식이다.

매번 로그인과 로그아웃을 수행하는 비용은 늘었지만, 적어도 공유 세션이 처리 중간에 만료되는 불확실성은 제거할 수 있었다. 다만 이것만으로는 외부 호출이 로컬 트랜잭션을 붙잡는 근본적인 문제가 해결되지 않았다.

## 외부 호출을 커밋 이후로 옮겼다

외부 호출을 트랜잭션 리스너의 `afterCommit()`으로 옮겼다. 실제 코드를 공개 가능한 형태로 단순화하면 다음과 같다.

```java
TransactionContext.getTransaction().addListener(new TransactionListener() {
    @Override
    public void afterCommit() throws SystemException {
        List<String> sessionTokens = sessionManager.generateSession();

        try {
            Document document = documentService.getDocument(docId);

            for (CallTarget target : targets) {
                ExternalRequest request = ExternalRequest.of(
                    docId,
                    document.getDocumentNumber(),
                    COMPLETE,
                    target.getPaymentStatus()
                );

                externalApi.patch(target.getUrl(), request, sessionTokens);
                callHistoryService.recordSuccess(docId, target);
            }
        } catch (Exception e) {
            callHistoryService.recordFailure(docId, e);
        } finally {
            sessionManager.removeSession(sessionTokens);
        }
    }
});
```

변경 후에는 결재 상태를 바꾸고 로컬 트랜잭션을 커밋해 락을 해제한 다음에야 외부 회계 시스템을 호출한다. 호출 결과를 기록하는 것도 원래 결재 트랜잭션과는 별도의 트랜잭션으로 분리했다.

먼저 우리 DB의 변경을 확정하고 락을 해제한 뒤 외부 시스템을 호출한다. 외부 시스템의 응답이 느려져도 그 지연이 원래 결재 트랜잭션의 락 유지 시간으로 이어지지 않게 됐다.

## afterCommit은 비동기가 아니다

이 변경은 외부 호출을 비동기로 만든 것이 아니다. `afterCommit()` 콜백은 요청을 처리하던 흐름에서 동기적으로 실행됐다. 따라서 외부 시스템이 느리면 사용자의 응답 시간은 여전히 길어질 수 있다.

대신 중요한 차이가 생겼다. 변경 전에는 외부 호출이 로컬 트랜잭션 커밋 전에 일어나서 호출 중에도 DB 락이 계속 유지됐고, 실패하면 로컬 트랜잭션도 함께 롤백할 수 있었다. 변경 후에는 외부 호출이 커밋 후에 일어나서 호출 중에는 이미 락이 풀려 있지만, 실패해도 이미 커밋된 로컬 트랜잭션은 되돌릴 수 없다. 사용자가 외부 호출 완료까지 기다려야 하는 건 두 경우 모두 같다.

이걸로 사용자 응답 시간이 줄어드는 건 아니다. 대신 외부 시스템의 지연이 내부 DB 락과 후속 요청으로 번지는 경로는 끊었다.

## 커밋 이후에만 얻을 수 있던 문서번호

외부 API의 원래 명세에는 문서번호가 필수 항목이 아니었다. 이후 업무 담당자가 외부 시스템에서도 문서를 쉽게 확인할 수 있도록 문서번호를 함께 보내달라고 요청했다.

그런데 문서번호는 우리 시스템에서 커밋 과정에야 채번됐다. 외부 호출을 커밋 전에 실행하면 아직 확정되지 않은 문서번호를 전달할 수밖에 없었다.

`afterCommit()`으로 호출을 옮긴 뒤에는 확정된 문서 정보를 다시 조회해 문서번호를 전달할 수 있었다. 조회 한 번이 추가됐지만, 확정되지 않은 값을 외부 시스템에 보내는 것보다 안전하다고 판단했다.

## 커밋 후 실패는 원래 트랜잭션으로 되돌릴 수 없다

외부 호출을 커밋 이후로 옮기면서 새로운 책임도 생겼다. 외부 호출이 실패해도 이미 완료된 우리 쪽 결재는 롤백할 수 없다. 우리 시스템에서는 결재가 완료된 상태인데 외부 시스템에는 반영되지 않은 상태가 남을 수 있다는 뜻이다.

그래서 이런 불일치를 발견하고 복구할 수단이 필요했다.

연계 API는 PATCH 방식이었다. HTTP의 PATCH 메서드 자체가 멱등성을 보장하는 것은 아니다. 다만 이 API는 동일한 문서 식별자에 요청받은 상태값을 다시 덮어쓰는 방식으로 동작했다. 같은 요청을 반복해도 데이터가 추가로 생성되거나 상태가 누적되지 않고 최종 값이 같았다.

이 특성을 이용해 실패한 요청을 다시 호출할 수 있었다.

초기 구현에는 외부 호출이 예외로 끝나면 이력 저장 코드까지 도달하지 못하는 문제가 있었다. 이후 성공 이력과 실패 이력을 별도로 기록하도록 위치를 변경했다. 덕분에 반영되지 않은 요청을 확인하고 같은 요청을 재처리할 수 있게 됐다 — 호출이 성공하면 성공 이력을 남기고, 실패하면 실패 이력을 남긴 뒤 그 대상만 골라 같은 PATCH 요청을 다시 보내는 식이다.

## 여러 전표를 처리할 때의 한계

한 결재 문서에는 여러 전표가 포함될 수 있었다. 이 전표들은 순차적으로 외부 시스템에 전달됐다.

다만 우리 쪽 이력 저장을 롤백하더라도, 이미 성공한 외부 API 호출까지 되돌릴 수는 없다. 세 번째 전표에서 호출이 실패했다면 앞의 두 전표는 이미 외부 시스템에 반영됐을 수 있다.

로컬 DB 트랜잭션만으로 여러 외부 호출의 원자성을 만들 수는 없다. 이 경우 실패 이력을 기준으로 각 전표의 반영 여부를 확인하고, 반영되지 않은 요청만 다시 처리해야 했다. 반복 호출 시 동일 상태로 갱신되는 API의 특성이 이 복구 방식을 가능하게 했다.

완전한 원자성이 필요했다면 연계 시스템의 배치 API나 보상 API, 분산 트랜잭션까지 같이 설계해야 했을 것이다. 하지만 연계 API의 명세를 변경할 수 없는 상황에서는 호출 이력과 재처리로 결과적 일관성을 확보하는 게 현실적인 선택이었다.

## 왜 완전한 비동기로 전환하지 않았나

완전히 비동기로 던져놓는 방식도 고민은 해봤다. 그런데 이건 전표문서였다. 당시 화면에는 "결재는 완료됐지만 외부 시스템에는 아직 반영되지 않은 상태"를 사용자에게 보여줄 방법이 없었고, 결재자와 회계 담당자는 요청이 끝난 시점에 연계 결과까지 확인할 수 있어야 했다. 그 시차를 허용하기 어려운 데이터였다.

게다가 연계 시스템 쪽 API 자체가 동기 호출 방식으로만 열려 있었다. 콜백이나 웹훅으로 결과를 나중에 받는 구조가 아니었고, 우리는 그 스펙에 맞춰 개발하는 입장이라 연계사 API 방식 자체를 바꿔달라고 요청할 수 있는 처지도 아니었다. 선택지는 사실상 동기 호출을 어디에 둘 것인가였고, 그중 우리 쪽 트랜잭션 밖으로 빼는 게 최선이었다.

## 트랜잭션 경계를 바꾸면 실패 처리도 다시 설계해야 한다

이번 문제의 핵심은 `afterCommit()`을 썼는지가 아니라, 우리가 통제할 수 없는 외부 시스템을 애초에 로컬 트랜잭션 경계 안에 둔 것이었다.

외부 호출을 커밋 이후로 옮기면서 DB 락 유지 시간은 줄었지만, 로컬 트랜잭션과 외부 시스템 사이의 원자성은 포기해야 했다. 그 대신 실패 이력, 반복 호출, 부분 성공 확인과 같은 복구 장치가 필요해졌다.

이번 일로 외부 시스템을 연동할 때는 API가 정상일 때만 생각하지 않는 버릇이 생겼다. 느려지거나 실패했을 때 우리 쪽 트랜잭션이 얼마나 오래 물려 있는지부터 먼저 보게 됐다.
