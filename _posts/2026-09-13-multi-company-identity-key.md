여러 법인으로 구성된 그룹사의 그룹웨어를 담당하고 있었다. 문제는 같은 사람이 여러 법인에 겸직으로 걸쳐 있는 경우, 인사시스템에서 그 사람을 가리키는 로그인 ID·연동키가 법인마다 전부 달랐다는 것이다. 그룹웨어 입장에서는 한 사람인데, 소스 시스템 입장에서는 서로 다른 사람 세 명처럼 보였다.

앞서 퇴직 유예 기간의 겸직 정보를 다룬 글을 썼는데, 사실 그건 이 작업이 끝난 뒤에 생긴 문제였다. 이 글은 그보다 먼저 있었던 일 — 애초에 "한 사람"을 어떤 값으로 정의할지 정하는 단계다.

## 왜 이걸 지금 풀어야 했는가

계기는 Teams 연동이었다. 사내 메신저를 하나로 통합하려면, 그 전에 "이 사람이 누구인지"부터 하나의 값으로 정의돼야 한다. 그런데 조직도 연동 로직은 법인별 사번을 기준으로 돌아가고 있었고, 한 사람이 두세 개의 사번을 가진 상태로는 애초에 "하나의 계정"이라는 개념을 만들 수가 없었다.

## 해법 — 통합 인적키라는 단일 식별자

인사시스템 쪽에는 이미 법인을 넘어 동일한 사람을 식별하는 통합 인적키가 있었다. 이 값을 그룹웨어 연동 데이터에 추가했다.

```java
private String personKey;          // 인사시스템 통합 인적키
private String currentCompanyYn;   // 현 소속법인 여부
private String userType;           // 본직·겸직·단일법인 구분
```

사용자 유형은 본직(통합 계정의 기본 소속), 겸직(같은 사람에게 연결되는 추가 소속), 단일법인(추가 소속이 없는 사용자) 세 가지로 나눴다.

이제 사번이 다르더라도 인적키가 같으면 같은 사람의 법인별 레코드로 연결할 수 있었다. 본직과 겸직을 고를 때는 인사시스템이 전달하는 사용자 유형과 현 소속 정보를 같이 썼다.

## 같은 인적키의 다른 소속을 찾는다

겸직 연동에서 필요한 판정 중 하나는 같은 사람이 다른 사번으로 이미 존재하는지 확인하는 것이었다. 실제 SQL의 핵심을 단순화하면 이렇다.

```sql
AND NVL(source_user.user_type, 'N') IN ('N', 'A')
AND EXISTS (
    SELECT 1
    FROM   gw_link_user_meta other_user
    WHERE  other_user.person_key = source_user.person_key
      AND  other_user.employee_no <> source_user.employee_no
      AND  other_user.status = 1
)
```

같은 인적키를 가진 다른 재직 레코드가 있는지 확인하는 조건이다. 사용자 유형이 겸직이거나 별도로 지정되지 않은 입력을 처리할 때 다른 소속의 존재를 확인하는 데 썼다.

다만 이 조건만으로 어느 레코드가 본직인지는 알 수 없다. 같은 사람에게 다른 소속이 있다는 것과, 그중 어떤 소속을 통합 계정의 기본값으로 고를지는 별개의 판단이다.

또 법인별로 같은 사번을 쓸 수 있다면 사번이 다르다는 조건만으로는 모든 겸직을 찾을 수 없다. 다법인 연동에서는 소속을 식별할 때 법인 코드와 사번을 같이 봐야 했다.

## 계정 하나에 법인별 소속을 연결했다

그룹웨어에서는 본직 정보를 사용자 마스터(`gw_user`)에 두고, 추가 소속은 겸직 테이블(`gw_user_add_job`)에 저장했다. 통합 사용자 계정 하나 아래에 본직으로 법인 A의 사번·로그인 ID가 붙고, 겸직으로 법인 B와 법인 C의 사번·로그인 ID가 각각 붙는 형태다. 각 겸직 레코드에는 회사, 부서, 직위 같은 소속 정보와 함께 해당 법인의 원래 사번과 로그인 ID를 보존했다.

로그인에 쓰는 그룹웨어 계정은 하나지만, 특정 법인의 조직도나 결재선에서 사용자를 표현할 때는 그 겸직 레코드의 정보를 참조하도록 했다. 법인별 사번과 로그인 ID를 없애지 않고, 하나의 계정 아래에 소속 정보로 연결한 것이다.

## 연계 시스템마다 보는 값이 달랐다

기존 법인별 사번과 로그인 ID를 지우지 않은 데는 실질적인 이유가 있었다. 그룹웨어에 붙어 있는 연계 시스템이 한둘이 아니었고, 각자가 사람을 식별하는 기준이 제각각이었다.

인사시스템은 통합 인적키로 사람을 보지만, 어떤 연계 시스템은 여전히 법인별 사번으로 대상을 찾는다. O365나 Teams는 또 자기 계정 체계를 쓴다. 그룹웨어 쪽에서 계정을 통합했다고 저쪽 시스템들이 같이 바뀌는 게 아니니, 각 법인에서 쓰던 원래 식별자는 그대로 살아 있어야 했다. 겸직 레코드에 사번과 로그인 ID를 보존한 게 결국 이 연계들을 끊지 않기 위한 장치였다.

연동 대상 여부도 시스템마다 따로 관리됐다. 같은 사람이라도 Teams는 연동되는데 O365는 아닐 수 있었고, 그 반대도 있었다. 그래서 연동 플래그를 시스템별로 따로 두고, 각 필드가 어느 연계에서 쓰이는 값인지 주석으로 명시해뒀다.

```java
private String officeYn;   // O365 연동 대상 여부
private String teamsYn;    // Teams 연동 대상 여부
```

주석 없이 `officeYn`, `teamsYn`만 보면 비슷한 플래그 두 개로 보인다. 나중에 누가 하나로 합치거나 한쪽 기준으로 다른 쪽까지 판단해버리면 엉뚱한 사람이 연동 대상에서 빠질 수 있었다. 필드 하나하나가 어느 시스템의 요구사항인지 적어두는 게, 나중에 이 코드를 볼 사람한테 줄 수 있는 최소한의 정보였다.

## 인적키의 중복은 범위에 따라 의미가 달랐다

통합 인적키를 도입하면서 검증도 추가했다. 키가 없는 데이터, 기존 사용자와 연결할 수 없는 데이터, 중복으로 처리되는 데이터를 구분해야 했다.

여기서 주의할 점은 같은 인적키가 여러 번 등장한다고 다 오류는 아니라는 것이다. 같은 사람이 여러 법인에 소속돼 있으면 원천 데이터와 겸직 레코드에서 같은 키가 반복되는 게 정상이다.

그래서 걸러야 하는 건 단순한 키 반복이 아니라 잘못된 계정 또는 소속의 중복이었다. 같은 인적키가 서로 다른 법인 소속으로 나타나는 건 정상적인 겸직이고, 같은 사람에게 별도의 통합 계정이 생기면 계정 중복, 동일한 법인·사번의 소속이 반복 생성되면 소속 중복, 인적키가 없어 기존 계정에 연결할 수 없으면 연결 실패다.

사람을 연결할 때는 인적키를 쓰고, 소속을 구분할 때는 법인과 사번을 쓴다. 이 두 검증 범위를 분리하지 않으면 정상적인 겸직을 중복 데이터로 걸러버리거나, 반대로 같은 소속을 여러 번 저장하게 된다.

## 계정을 통합해도 업무 소속은 하나가 아니었다

이 설계 이후 결재선 처리에서 본직 정보로 잘못 결재되는 문제를 발견했다.

사용자의 로그인 계정이 하나가 되자, 일부 기존 코드는 그 계정의 본직 정보만 조회했다. 하지만 사용자가 법인 B의 겸직으로 결재하고 있다면 부서와 직위, 연계 사번도 법인 B의 값이어야 한다.

같은 사람이 맞는지 확인하는 것과, 어떤 소속으로 업무를 수행하는지 확인하는 것은 별개의 문제였다. 누가 처리하는지는 통합 사용자 계정이 답하고, 어느 소속으로 처리하는지는 본직 또는 선택된 겸직이 답한다.

계정 통합만으로 결재 로직까지 자동으로 맞아지지는 않았다. 결재선과 조직도처럼 소속에 따라 동작이 달라지는 기능에서는 통합 사용자뿐 아니라 지금 업무에 적용되는 소속도 같이 전달하고 조회해야 했다.

## 식별자를 바꾸는 일은 참조 방식을 바꾸는 일이었다

이번 작업에서 가장 중요한 선택은 사번을 없앤 게 아니라, 사번의 역할을 법인별 소속 식별자로 한정한 것이었다. 사람은 통합 인적키로 연결하고, 법인별 사번과 로그인 ID는 각 소속에 남겼다. 덕분에 하나의 계정으로 로그인하면서도 여러 법인의 업무 신원을 유지할 수 있었다.

그런데 새 필드를 추가하고 데이터 구조를 바꾸는 것만으로 작업이 끝나지는 않았다. 기존 코드는 여전히 계정 하나와 소속 하나가 같다는 전제로 짜여 있었고, 그 전제가 남아 있는 조회와 결재 로직을 찾아 고치는 일이 계속 뒤따랐다.

퇴직 유예 기간 동안 겸직 정보를 유지해야 하는 문제도 이 구조 위에서 나온 것이다. 본직 계정 하나가 법인별 신원을 겸직 레코드로 거느리는 형태가 잡히고 나니, 그다음엔 그중 하나가 유예 상태로 남는 경우를 어떻게 다룰지가 숙제로 넘어왔다.
