개발하다 보면 하나의 테스트 계정에 여러 개발자가 같이 붙는 경우가 있다. 그래서 중복 로그인을 허용해 뒀는데도 "다른 PC에서 로그인하여 로그아웃합니다"라는 메시지를 보고 튕기는 일이 가끔 생겼다. 나도 설정을 바꿔둔 뒤에 몇 번이나 튕겼다. 다시 확인해 보니 관리자 화면의 설정도, DB에 저장된 값도 허용이었다. 설정은 맞는데 동작이 반대라서 오류로 보고 수정에 들어갔다.

중복 로그인 차단은 Redis의 `single_session:{userId}` 키로 하고 있었다. 단일 세션 모드에서 로그인하면 이 키에 현재 세션의 `cacheId`를 저장한다. 이후 요청을 처리하는 필터가 Redis 값과 현재 세션의 `cacheId`를 비교하고, 다르면 다른 곳에서 로그인한 걸로 보고 기존 세션을 끊는다.

허용 모드에서는 이 키가 아예 없어야 했다. 그래서 제일 먼저 의심한 건 설정을 바꾼 뒤에도 남아 있는 키였다.

## 설정은 바뀌었는데 키는 그대로였다

사용자가 본인 환경설정에서 옵션을 바꾸는 경로부터 봤다. 서비스는 설정 엔티티를 갱신한 뒤, 트랜잭션이 커밋되고 나서 이전 값과 새 값을 비교해 키를 정리하게 되어 있었다.

```java
userConfig.updateConfig(request);
syncSessionKey(request, userConfig, userId);

// 커밋 이후 실행되는 콜백 내부
if (!userConfig.getAllowMultiSession() && request.getAllowMultiSession()) {
    // 차단 → 허용: 키 삭제
} else if (userConfig.getAllowMultiSession() && !request.getAllowMultiSession()) {
    // 허용 → 차단: 현재 세션의 cacheId 저장
}
```

콜백에 넘긴 `userConfig`가 변경 전 값의 복사본이 아니라 같은 엔티티의 참조였다. `updateConfig()`가 값을 바꾼 다음에 콜백이 도니까, 콜백이 이전 값이라고 읽는 것도 이미 새 값이었다. 두 전환 조건이 어느 쪽도 성립하지 않았다.

DB 설정은 저장되는데 키는 정리되지 않았던 이유가 이거였다.

수정은 변경 전 값을 먼저 복사해 두는 것이었다.

```java
Boolean previous = userConfig.getAllowMultiSession();
userConfig.updateConfig(request);
syncSessionKey(request, previous, userId);
```

관리자 화면에서 같은 옵션을 바꾸는 경로도 따로 봤다. 원래 이 경로는 새 설정이 차단일 때만 키를 지웠고, 허용으로 바꿀 때는 기존 키를 그대로 남겼다. 그런데 관리자 경로에는 대상 사용자의 현재 세션 `cacheId`가 없다. 모르는 세션의 값을 임의로 저장할 수는 없어서, 설정이 바뀌면 기존 키를 일단 지우고 다음 로그인 때 최신 설정대로 다시 만들게 했다.

대신 관리자가 차단으로 바꾼 직후부터 그 사용자가 다시 로그인하기 전까지는 단일 세션 강제가 완전하지 않다. 이 구간은 막을 방법이 없어서, 설정을 바꾼 관리자에게 다음 로그인부터 적용된다는 안내를 띄우기로 했다.

## 만료될 키를 토큰 갱신이 계속 살렸다

설정 변경 경로를 고쳐도 이미 남아 있는 키가 사라지지는 않는다. 원래라면 TTL이 지나면 만료돼야 하는데, 허용 모드 사용자에게서 키가 계속 발견됐다.

토큰 갱신 경로를 따라가 보니 TTL을 연장하는 쪽 조건이 반대로 되어 있었다.

```java
public void extendSessionKeyTTL(String userId, String cacheId) {
    if (!isDuplicateLogin(userId)) return;
    // cacheId가 일치하면 키의 TTL 연장
}
```

`isDuplicateLogin()`은 이름만 보면 지금 중복 로그인 상태인지 묻는 것 같은데, 실제로는 중복 로그인을 허용하는지를 반환한다. 그래서 허용 모드에서는 남아 있으면 안 되는 키의 TTL을 늘리고, 차단 모드에서는 정작 필요한 키를 연장하지 않고 있었다.

키가 한 번 잘못 남으면 브라우저에서 토큰을 갱신할 때마다 수명이 계속 늘어났다. 반대로 차단 모드에서는 키가 먼저 만료돼서 차단 기준 자체가 사라질 수 있었다.

조건을 바로잡으면서, 허용 모드에서 키를 발견하면 지우도록 했다.

```java
if (isDuplicateLogin(userId)) {
    if (StringUtils.isNotEmpty(cachedId)) {
        deleteSessionKey(userId);
    }
    return;
}

if (cacheId.equals(cachedId)) {
    redisService.extendTTL(sessionKey, KEY_TTL, TimeUnit.SECONDS);
}
```

설정 변경 쪽이 새 키가 잘못 생기는 걸 막는 작업이었다면, 토큰 갱신 쪽은 이미 남은 키를 발견했을 때 치우는 작업이었다.

## 몇 주 뒤, 키가 다시 생겼다

여기까지 하고 중복 로그인 문제는 끝났다고 생각했다. 그런데 몇 주 뒤 로컬에서 기안 화면을 개발하다가 같은 메시지를 또 봤다. 계정은 허용 모드였다. 재로그인 직후엔 괜찮다가 잠시 뒤 다시 로그아웃됐다.

로그를 시간순으로 비교해 보니 재로그인 후처리에서는 키를 정상적으로 지웠다. 그런데 1분 반쯤 뒤에 필터가 같은 키를 다시 읽었다. 그 사이 로그인이나 설정 변경 로그는 없었다. 다른 어딘가에서 키를 만들고 있었다.

범인은 통합 테스트 픽스처였다. 테스트용 토큰을 만드는 `TestTokenFactory`가 토큰을 만들 때마다 랜덤 `cacheId`로 키를 저장하고 있었다. 테스트 계정은 개발자들이 브라우저에서도 쓰는 공용 관리자 계정이었고, Redis도 팀 공용 서버였다.

누군가 통합 테스트를 돌리면 테스트가 기록한 `cacheId`가 브라우저 세션의 값과 달라진다. 필터는 이걸 진짜 중복 로그인으로 판단했다. 테스트가 만든 키의 TTL은 30분이었다.

## 키를 지우는 코드가 있어도 요청은 먼저 튕겼다

토큰 갱신 때 키를 지우도록 해뒀는데 왜 회복이 안 됐을까.

프론트의 자동 토큰 갱신은 토큰 만료 응답에서만 시작됐다. 중복 로그인 응답을 받으면 바로 안내 화면으로 넘어가 버려서, 키를 지우는 코드가 있는 토큰 갱신 경로까지 가지 못했다.

더 근본적으로는 필터가 Redis 값과 현재 `cacheId`가 다르면 허용 설정을 확인하지도 않고 바로 요청을 거부했다. 허용 모드에 잘못된 키가 생겼을 때 걸러줄 곳이 없었던 셈이다.

그래서 필터의 불일치 분기에 설정 확인을 넣었다.

```java
if (hasCachedId && !cachedId.equals(currentCacheId)) {
    if (sessionService.isDuplicateLogin(userId)) {
        sessionService.deleteSessionKey(userId);
        filterChain.doFilter(request, response);
        return;
    }

    // 차단 모드의 기존 중복 로그인 처리
}
```

설정 조회는 `cacheId`가 다를 때만 도니까 정상 요청 경로에는 추가 조회가 없다. 허용 모드면 잘못 남은 키로 보고 지운 뒤 통과시키고, 차단 모드면 기존처럼 거부한다.

이 수정은 테스트부터 작성했다. 허용 모드에서 키가 현재 `cacheId`와 다르면 키를 지우고 통과해야 하고, 차단 모드에서 다르면 중복 로그인 응답이 나가야 한다. 차단 모드에서 키가 같거나 아예 없으면 설정 조회 없이 그냥 통과해야 한다. 이 네 경우를 먼저 테스트로 만들어두고 필터를 고쳤다.

테스트 픽스처는 자기가 만든 키를 테스트 컨텍스트가 끝날 때 `@PreDestroy`에서 정리하게 바꿨다. 프론트에서는 중복 로그인 응답을 받으면 토큰 갱신과 원래 요청 재시도를 딱 한 번만 허용했고, 재시도 후에도 같은 응답이면 기존 중복 로그인 화면을 띄웠다. 이렇게 하니 복구되는 경우와 진짜 중복 로그인을 화면에서도 구분할 수 있었다.

프론트에는 유닛 테스트 환경이 없어서 Redis에 가짜 `cacheId`를 넣어 수동으로 확인했다. 허용 모드에서는 화면이 유지되면서 키가 지워지는지, 차단 모드에서는 중복 로그인 안내가 뜨는지 각각 봤다.

## 정리 코드로 막을 수 없는 구간이 남는다

테스트가 만든 키를 `@PreDestroy`로 치우게 했지만, 이 콜백은 스프링 컨테이너가 정상적으로 내려갈 때만 실행된다. 테스트 도중 프로세스를 강제로 종료하거나 IDE에서 실행을 끊으면 컨테이너 종료 훅 자체가 돌지 않는다. 애플리케이션 코드로 붙잡을 수 있는 시점이 아니라서, 키가 남는 경우는 정리 코드가 아니라 필터 쪽에서 받아내는 수밖에 없었다.

컨테이너가 언제 내려가는지도 테스트 코드가 정하지 못한다. 스프링은 같은 설정의 테스트 컨텍스트를 캐시해 두고 여러 테스트 클래스에서 재사용하기 때문에, 테스트 메서드가 끝났다고 컨텍스트가 바로 닫히지 않는다. 정리 시점이 뒤로 밀리는 동안 다른 로그인 흐름이 같은 키를 새 값으로 갱신할 수 있고, 그러면 `userId`만 보고 지우는 정리 코드가 정상 데이터까지 지운다. 그래서 정리 시점에 Redis의 현재 값을 확인하고 테스트가 만든 `cacheId`일 때만 지우게 해뒀다.

테스트가 사람이 쓰는 계정과 Redis 키 공간을 같이 쓰는 것도 개발 환경 구성에서 오는 제약이었다. Redis는 팀 공용 서버였고 테스트 계정도 개발자들이 브라우저에서 같이 쓰는 계정이라, 테스트 코드 안에서 이 공유를 없앨 방법은 없었다. 계정과 권한 데이터를 새로 준비해야 하는 일이었다. 운영 환경에서는 재현될 일이 드물다고 보고, 일단 연구소에 오류 건으로 전달했다.

## 키를 건드리는 경로가 하나가 아니었다

솔직히 처음 고쳤을 때는 끝났다고 생각했다. 몇 주 뒤 내 화면에서 다시 튕기는 걸 보고 나서야 이 키를 누가 만들고 누가 늘리고 누가 지우는지 처음부터 다시 따라갔다.

실제로는 같은 키를 네 군데서 제각각 다르게 다루고 있었고, 한 군데를 고쳐도 다른 데서 같은 증상이 다시 만들어졌다.

캐시는 값을 넣는 코드가 제일 짧고, 그래서 보통 거기까지만 보고 넘어간다. 정작 문제가 된 건 그 값이 언제 사라지느냐였다. 이번 건도 저장하는 쪽은 멀쩡했고 지우는 쪽과 연장하는 쪽이 서로 어긋나 있었다. 그 뒤로는 캐시를 쓸 때 저장 코드보다 만료와 삭제 조건을 먼저 정해두고 시작한다.
