전자결재 기능을 모바일 API로 제공하는 프로젝트였다. 기존 PC 웹은 세션 기반 로그인을 썼지만, 모바일 API에는 요청마다 `Authorization` 헤더로 토큰을 받아 인증하는 방식을 붙였다.

JWT를 직접 검증 로직에 연결해본 건 이때가 처음이라 재밌었다. 토큰을 파싱하는 코드는 길지 않았는데, 검증 실패를 앱에 어떻게 알려줄지가 더 고민이었다. 이후 스프링으로 넘어가면서 JWT로 토큰을 만들 일이 생겼을 때 이 작업이 떠올랐다.

## 토큰이 만료됐는가, 검증 자체가 실패했는가

JWT 라이브러리인 `jjwt`는 서명이나 만료 시간을 검증하고, 문제가 있으면 예외를 던진다. 모든 예외를 하나의 인증 실패로 바꾸면 서버는 간단해진다. 대신 앱은 토큰의 유효 기간이 끝난 건지, 형식이나 서명이 잘못된 건지 알 수 없게 된다.

그래서 만료와 그 밖의 검증 실패에 서로 다른 애플리케이션 오류 코드를 줬다. 핵심 흐름을 단순화하면 이렇다.

```java
public static String validateToken(String authorization)
        throws BusinessException {
    try {
        String token = authorization.substring(
            authorization.indexOf(" ") + 1
        );

        Claims claims = Jwts.parser()
            .setSigningKey(key.getBytes("UTF-8"))
            .build()
            .parseClaimsJws(token)
            .getBody();

        return (String) claims.get(USER_CLAIM);

    } catch (ExpiredJwtException e) {
        throw new BusinessException(EXPIRED_TOKEN);
    } catch (Exception e) {
        throw new BusinessException(INVALID_TOKEN);
    }
}
```

`ExpiredJwtException`은 유효 기간이 지난 토큰이다. 그 밖의 오류는 당시 구현에서 무효 토큰으로 묶었다. 호출부는 이걸 앱과 약속한 오류 코드로 바꿨다.

```java
if (EXPIRED_TOKEN.equals(exception)) {
    errorCode = ErrorCodes.TOKEN_EXPIRED;
} else if (INVALID_TOKEN.equals(exception)) {
    errorCode = ErrorCodes.TOKEN_INVALID;
}
```

두 경우 다 인증에 실패했으니 보호된 API 요청은 허용하지 않는다. 차이는 앱이 실패 이후에 어떤 흐름을 고를 수 있느냐였다.

앱이 실제로 이 코드를 받아서 어떻게 처리했는지는 내가 구현한 부분이 아니라 모른다. 서버에서 한 건 앱 쪽에서 우리 상황을 파악할 수 있을 만큼의 예외값을 넘겨주는 데까지였다.

## 구분은 클라이언트의 대응을 위한 것이었다

만료는 정상적으로 발급된 토큰에서도 시간이 지나면 생긴다. 앱에 갱신 절차가 있으면 그 절차를 시작하면 되고, 없으면 다시 로그인하도록 안내하면 된다.

반면 서명이나 형식 검증에 실패한 토큰은 같은 토큰으로 몇 번을 더 보내도 달라지지 않는다. 저장해둔 인증 정보를 버리고 로그인부터 다시 하는 수밖에 없는 상황이다.

여기서 만료 오류 코드를 내려준다고 자동 갱신 기능까지 구현된 건 아니다. 이 작업의 범위는 실패 원인을 구분해서 전달하는 데까지였다. 실제로 토큰을 재발급받을 수 있는지는 별도의 갱신 API와 앱의 인증 흐름에 달려 있다.

HTTP 상태는 두 경우 모두 인증 실패인 `401`로 둘 수 있다. 세부 원인은 응답 본문에 담은 애플리케이션 오류 코드로 전달했다. `401` 하나로는 세부 원인을 표현할 수 없지만, 그렇다고 만료를 성공이나 권한 부족으로 처리할 이유도 없다.

## 토큰 이후의 사용자 조회도 별개로 다뤘다

토큰의 서명과 만료 시간이 멀쩡해도, 토큰에 담긴 사용자를 지금 시스템에서 못 찾을 수 있다. 그래서 로그인 실패, 토큰 만료, 무효 토큰, 사용자 없음에 각각 다른 코드를 뒀다.

토큰 검증 실패와 사용자 조회 실패는 터지는 지점이 다르다. 앞은 받은 인증 정보 자체를 믿을 수 없는 경우고, 뒤는 토큰은 검증했는데 현재 사용자 데이터와 연결하지 못한 경우다.

사용자 없음까지 내려준 건 앱 쪽 관리자도 사용자 유무 정도는 확인할 수 있어야 했기 때문이다. 이 코드를 보려면 이미 서명과 만료 검증을 통과한 토큰이 있어야 하니, 아무나 계정 존재 여부를 떠볼 수 있는 응답은 아니었다. 로그인 화면처럼 인증 전 단계에서 같은 구분을 노출했다면 유효한 계정을 추측하는 단서가 됐겠지만, 여기는 토큰을 이미 가진 쪽만 도달하는 지점이었다.

## 코드를 다시 보며 발견한 보완점

지금 다시 짠다면 몇 군데는 더 좁게 처리했을 것 같다.

우선 `substring(indexOf(" ") + 1)`은 `Bearer` 접두어를 검증하지 않는다. 공백이 없거나 다른 인증 방식이 들어와도 엉뚱한 문자열을 토큰으로 넘기게 된다. 헤더가 `Bearer <token>` 형식인지부터 확인했어야 했다.

`catch (Exception)`도 마찬가지다. 서명 오류와 형식 오류뿐 아니라 키 설정 문제, 사용자 클레임 처리 오류 같은 서버 내부 문제까지 전부 무효 토큰으로 덮어버린다. JWT 검증 예외와 헤더 형식 오류만 따로 분류하고 나머지는 서버 오류로 드러냈으면 원인 추적이 쉬웠을 것 같다.

파싱에 성공했다는 것만으로 인증이 끝나는 것도 아니었다. 필요한 사용자 식별 클레임이 있는지, 그 사용자가 지금 유효한지까지 봤어야 했다. 서명 키의 구성과 길이가 쓰는 알고리즘에 맞는지도 그때는 따로 확인하지 않았다.

## 지금은 로그까지만 상세하게 남긴다

지금 그룹웨어에서 혼자 처리할 때는 오류 상황을 상세히 적는 건 로그까지만 하고, 사용자에게는 그 내용을 그대로 내려보내지 않는다.

모바일 앱에는 만료와 무효를 구분해서 넘길 이유가 있었다. 받는 쪽에서 원인에 따라 다르게 처리할 여지를 남겨야 했으니까. 그런데 사람이 보는 화면에 "서명 불일치" 같은 내부 원인을 띄워봐야 사용자가 할 수 있는 게 없고, 인증 실패의 원인을 구체적으로 알려주는 건 그 자체로 공격자에게 힌트가 된다. 화면에는 다시 로그인해달라는 정도만 보여주고, 어디서 왜 막혔는지는 로그에 남겨서 나중에 추적할 때 쓴다.

상세하게 나누는 거랑 상세하게 보여주는 건 다른 얘기였다는 걸, 이 두 상황을 다 겪고 나서야 알았다.
