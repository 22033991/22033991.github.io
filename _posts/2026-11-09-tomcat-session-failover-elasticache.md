2022년 말부터 이듬해까지 결제 서비스를 하는 고객사의 그룹웨어 업그레이드를 맡았다. 서버를 두 대로 이중화하면서 애플리케이션 캐시는 Ehcache에 두고, HTTP 세션은 톰캣 세션 클러스터링으로 복제하기로 했다. 별도 프록시 없이도 톰캣에서 세션을 복제할 수 있다는 설명을 듣고 그렇게 진행했다.

처음 이상하다고 느낀 건 배포할 때였다. 한 대를 내려도 나머지 한 대가 요청을 받으니 사용자는 아무것도 모를 줄 알았다. 그런데 배포할 때마다 갑자기 로그아웃됐다는 문의가 들어왔다.

## 로그아웃된 이유

원인을 따라가 보니 로그인 상태를 확인하는 데 필요한 정보가 서버마다 Ehcache에 따로 들어 있었다. 서버 A를 내리면 요청은 B로 잘 넘어갔는데, B에는 A가 갖고 있던 인증 정보가 없었다. 사용자는 하던 일을 이어가려다 로그인 화면을 보게 된 것이다.

나중에 알고 보니 톰캣이 노드끼리 복제해 주는 건 HTTP 세션뿐이었다. 애플리케이션이 로컬 캐시에 따로 넣어 둔 정보는 복제 대상이 아니었다. 요청만 넘어가면 될 줄 알았는데, 넘겨받은 서버가 로그인 상태를 되살릴 정보까지 갖고 있어야 했다. [Apache Tomcat 세션 복제 문서](https://tomcat.apache.org/tomcat-9.0-doc/cluster-howto.html)

고객사 환경 때문에 저장 구조를 바꾸기는 어려웠고, 로드밸런서에 스티키 세션을 걸어 같은 사용자는 되도록 같은 서버로 가게 했다. 문의는 확 줄었다. 그래도 그 서버를 내리면 거기 붙어 있던 사용자는 다시 로그인해야 했다. 솔직히 해결했다기보다는 덜 보이게 만든 쪽에 가까웠다.

## 세션을 Redis에 둔다면

그때 로그인에 필요한 정보를 공용 저장소에 뒀다면 서버 A를 내려도 B가 같은 정보를 읽었을 것이다.

지금 하는 프로젝트에서도 Redis를 쓰고 있다. 다만 조회 속도 때문에 붙인 캐시라 한 대로만 운영하고, HTTP 세션은 여기에 두지 않는다. 중복 로그인을 막는 키를 Redis에 두면서 키 수명주기 때문에 고생한 이야기는 따로 썼다.

LT 프로젝트에서는 와일드카드 조건이 지워야 할 키 일부를 놓치는 바람에 오래된 캐시가 남아 있던 적도 있었다. 조건을 고쳐서 남은 키는 지웠는데, 프레임워크 안에 이런 삭제 경로가 얼마나 더 있을지 계속 신경이 쓰였다. 그때는 지워야 할 키가 남아 있는 게 문제였다. 세션을 넣는다면 남아 있어야 할 키가 사라지는 것도 걱정해야 한다.

캐시는 비어도 DB에서 다시 읽으면 되지만, 세션은 날아가면 사용자가 바로 로그아웃된다. 지금처럼 Redis가 한 대뿐인데 세션까지 넣으면, 애플리케이션 서버가 몇 대든 Redis 한 대가 죽는 순간 전체 사용자가 영향을 받는다.

## ElastiCache에서는

AWS SAA를 준비하면서 ElastiCache를 공부할 때 처음 걸린 건 "Redis 영속성이 스냅샷 얘기인가?"였다. 찾아보니 방식이 두 가지였다. RDB는 특정 시점의 데이터를 스냅샷으로 떠 두고, AOF는 데이터를 바꾼 명령을 로그로 쌓는다. RDB로 복구하면 마지막 스냅샷 뒤의 변경분은 잃을 수 있다. AOF를 `appendfsync everysec`으로 두면 장애 때 잃는 건 최근 1초 정도지만 파일이 보통 RDB보다 크다. [Redis 영속성 문서](https://redis.io/docs/latest/management/persistence/)

그런데 배포 때 겪은 일을 생각하면, 나한테 더 궁금했던 건 백업이 언제였냐보다 프라이머리가 내려갔을 때 누가 요청을 받느냐였다. ElastiCache의 노드 기반 Redis OSS나 Valkey 구성에서는 다른 가용 영역에 레플리카를 두고 Multi-AZ를 켤 수 있다. 프라이머리가 죽으면 ElastiCache가 레플리카를 새 프라이머리로 올린다. 스냅샷은 데이터를 되살리는 용도고, 서비스를 이어가게 해 주는 건 이 페일오버 쪽이었다. [AWS ElastiCache 장애 대응 문서](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/disaster-recovery-resiliency.html)

다만 레플리카는 비동기로 따라오기 때문에, 페일오버 직전에 쓴 데이터가 아직 넘어가지 않았을 수 있다. 방금 로그인한 사용자의 세션이 복제되기 전에 프라이머리가 내려가면 그 사용자는 다시 로그인해야 한다. 내가 맡았던 서비스라면 장애 직전 몇 명이 다시 로그인하는 정도는 감수할 만하다고 봤다. 찾아보니 올해부터 Valkey 9.0 이상에서는 동기 쓰기 옵션을 켜면 성공 응답을 받은 쓰기는 장애가 나도 남는다고 한다. 대신 쓰기 지연이 마이크로초 단위에서 한 자릿수 밀리초로 늘어난다. 몇 명을 다시 로그인시키는 게 나은지, 쓰기마다 조금씩 느려지는 게 나은지는 서비스마다 다를 것 같다. [AWS Multi-AZ 문서](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/AutoFailover.html) · [AWS 내구성 옵션 문서](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/Durability.Options.html)

Memcached는 처음부터 뺐다. 노드 기반 Memcached는 노드끼리 복제를 하지 않아서, 한 노드가 죽으면 거기 있던 세션도 같이 사라진다. 저장소를 애플리케이션 서버 밖으로 빼도 결국 처음 겪은 문제를 다시 만나게 된다. [AWS ElastiCache 복제 문서](https://docs.aws.amazon.com/AmazonElastiCache/latest/dg/WhatIs.Components.html)

다시 그 그룹웨어를 배포한다면 서버 A를 내리기 전에 A에서 먼저 로그인해 볼 것 같다. 요청이 B로 넘어간 뒤에도 같은 사용자가 하던 일을 그대로 할 수 있는지 확인하고 싶다. 세션을 Redis에 둔다면 Redis 프라이머리를 바꿀 때도 같은 걸 해 볼 생각이다.
